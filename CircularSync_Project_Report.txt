CIRCULARSYNC: AN AUTOMATED CAMPUS CIRCULAR PARSING DAEMON AND QUERY SYSTEM

A Project Report on the Design and Implementation of a Concurrent,
File-System-Driven Notice Management Engine in Java

November 2026


ABSTRACT

Colleges issue a large volume of circulars every semester through many
unstructured channels, and these circulars are rarely ranked by urgency, so
students routinely miss deadlines with academic or career consequences. This
report presents CircularSync, a Java application that treats every circular as
a structured document dropped into a monitored directory. A daemon built on the
Java NIO WatchService detects new files in real time, a fixed-size thread pool
fed by a blocking queue parses and validates them concurrently, and a
thread-safe in-memory registry keeps every active notice sorted by priority and
deadline. Notices are modelled through an abstract base class with three
subclasses, an interface defining the processing contract, and custom checked
exceptions that make every failure explicit. All outcomes are recorded in an
asynchronous audit log. The system was verified with an eighteen-case
automated test suite and live runs, and placed under Git version control.


CHAPTER 1: INTRODUCTION AND PROBLEM STATEMENT

1.1 Background

An engineering college of moderate size issues several hundred circulars in an
academic year. The Controller of Examinations publishes schedules and
hall-ticket instructions, the Training and Placement Cell announces recruitment
drives with tight registration windows, and student clubs advertise workshops
and competitions. Each office chooses its own medium: a page on a notice board,
an email attachment, a message in a class group or a post on the college
portal. Information that is individually well written becomes collectively
chaotic. Students miss hall-ticket windows, register late for placement drives
and learn about workshops after the seats are full.

1.2 Bottlenecks in the Existing Process

Three weaknesses explain the failure. First, circulars have no common
structure: the deadline, the issuer and the expected action are buried in
prose and cannot be extracted mechanically. Second, there is no
prioritisation: an optional quiz and a mandatory end-semester examination
arrive with the same visual weight. Third, there is no single queryable store,
so a student cannot simply ask which deadlines fall within the next week. A
quieter weakness is the lack of accountability: when a circular is corrected
or withdrawn, there is no record of when the change happened.

1.3 Objectives

CircularSync was designed to accept circulars in a simple, human-editable
structured format in plain text or Markdown; to detect new or edited circulars
automatically within seconds; to process many circulars concurrently so that
bursts do not create a backlog; to reject malformed and expired circulars with
a clear explanation; to rank active circulars by a transparent priority score;
to answer queries by category, keyword, deadline window and identifier; and to
record every event in a durable audit trail.

1.4 Scope

The project delivers a command-line application in standard Java with no
third-party libraries, covering three categories: examination, placement and
club notices. Extraction from unstructured PDFs, authentication and graphical
interfaces are left as future work.


CHAPTER 2: ARCHITECTURAL DESIGN AND SYSTEM FLOW

2.1 Architectural Overview

CircularSync follows a producer and consumer architecture. A watcher observes
the incoming directory and produces work items; a work queue buffers them; a
worker pool converts each file into a notice object; and a registry stores,
indexes and queries notices. Two supporting components complete the design: an
audit logger that records events without blocking the threads producing them,
and a command console that translates user commands into registry queries.

The components are deliberately decoupled. The watcher knows nothing about
parsing, the workers know nothing about the console, and the registry knows
nothing about files. Each communicates through a narrow interface: a path on a
queue, a notice passed to a register method, or a line passed to the logger.
This allows each part to be tested in isolation and keeps the concurrency model
simple.

2.2 Life Cycle of a Notice

An issuing office saves a file such as sample_exam.txt into incoming_notices.
The operating system reports a creation event, usually followed by
modification events. The watcher thread wakes, resolves the file name against
the watched directory, checks the extension, offers the path to the work queue
and returns to waiting.

A worker thread takes the path and waits until the file has stopped changing,
reading its size and modification time until two consecutive readings agree.
If this fingerprint equals the one recorded for the last processing of the same
path, the event is a duplicate and is discarded. Otherwise the parser reads the
content, detects the type from the TYPE header, constructs the matching
subclass and runs validation, metadata parsing and the deadline check. The
registry reports whether the notice was added, replaced an earlier version of
the same file, or duplicated existing content. The worker writes an audit
record and notifies listeners, which in daemon mode print the new notice.

A deleted file causes its notice to be withdrawn. An edited file replaces its
old version atomically. A file that fails validation is audited, and any
earlier valid version of it is withdrawn so that stale information is not
shown.

2.3 Operating Modes

Scan mode queues every existing file, waits for the pipeline to drain, prints
the ranked board and exits. Query mode does the same but runs a single query,
which suits scripting. Daemon mode keeps the watcher running and offers an
interactive prompt while new files continue to arrive; it can also run
unattended for a fixed duration. All modes share one pipeline, so behaviour
verified in one holds in the others.

2.4 Design Decisions

The registry is kept in memory because active circulars number in the
hundreds; the source files remain the authoritative record, so the registry can
always be rebuilt by rescanning. The file system is the integration point
because every office can drop a file into a shared folder. Finally, the
priority score is computed once at parse time and cached. It depends on the
reference date, and recomputing it during comparisons could leave the sorted
collection internally inconsistent as the date changed.


CHAPTER 3: OBJECT-ORIENTED DESIGN PATTERNS

3.1 The Processable Interface

The interface Processable declares validateFormat, which checks structural
shape; parseMetadata, which converts header values into typed fields; and
isProcessed, which reports completion. Both of the first two declare the
checked InvalidNoticeFormatException, forcing every implementation to report
problems uniformly. Separating validation from parsing lets cheap structural
checks reject most bad input before any conversion, and lets error messages
distinguish a wrongly shaped file from one with wrong values.

3.2 The Abstract Base Class Notice

The abstract class Notice implements Processable and Comparable. It holds the
state shared by every circular: source file name, raw content, reference date,
headers, body, identifier, title, issuer, issue date, deadline, priority
keywords and cached score.

Notice provides final implementations of validateFormat and parseMetadata, so
subclasses cannot weaken the common checks. Within them it applies the
Template Method pattern: common logic runs first, then calls the protected
abstract hooks getTypeSpecificRequiredHeaders and parseTypeSpecificMetadata.
The base class controls the order of operations while subclasses supply only
what differs. Two public abstract methods, calculatePriorityScore and
formatSummary, express behaviour that differs entirely between categories, and
getCategory ties each subclass to a constant of the NoticeCategory enumeration.

The base class also offers helpers for scoring. The method urgencyPoints
implements a stepped curve awarding forty points when the deadline is at most
one day away, thirty-two within three days, twenty-four within a week, fourteen
within two weeks, six within a month and two otherwise. The method
keywordPoints sums the weights of the notice's keywords from a table supplied by
the subclass. Stepped values were chosen because they are easy to explain to
students and administrators.

3.3 Inheritance and Method Overriding

ExamNotice adds a course code, examination date, venue and optional
examination type. Its score combines a category base of thirty, the urgency of
the action deadline, a proximity bonus for the examination date, and weights
for keywords such as mandatory, hall-ticket and end-semester. The sample
examination notice, six days from its deadline and twelve from its
examination, scored thirty plus twenty-four plus six plus twenty-six, giving
eighty-six.

PlacementNotice adds company, role, eligibility and optional package, minimum
grade point average and drive date. Its base is twenty-five, plus urgency, a
compensation band bonus of five, ten or fifteen points, and keyword weights for
terms such as dream and registration. The sample placement notice scored
seventy-seven.

ClubNotice adds club name, event date, venue and an optional seat limit. Its
base is only ten so that optional activities never bury mandatory ones, and it
receives three quarters of the urgency points, keyword weights for terms such
as hackathon and workshop, and a scarcity bonus of four points when seats are
limited to sixty or fewer. The sample club notice scored twenty-nine.

Each subclass overrides formatSummary to present the fields relevant to its
category. The console and the board snapshot call formatSummary through a
reference of the base type, and dynamic dispatch selects the right version at
run time. Code that renders the board therefore needs no knowledge of which
notice types exist.

3.4 Natural Ordering and Identity

The natural order places the highest score first, then the earliest deadline,
then title, then identifier. The final comparison makes the order total, which
a TreeSet requires to retain distinct notices. The identifier combines a
three-letter category prefix with the first ten hexadecimal characters of a
SHA-256 digest of the content, so identical files share an identifier and
duplicates are detected cheaply. The equals and hashCode methods use the
identifier, keeping them consistent with the ordering.

3.5 Supporting Patterns

The parser's protected createNotice method is a Factory Method mapping a
category to its subclass, overridable to add categories. The daemon's index
listeners implement the Observer pattern, and the console applies a simple
Command pattern, dispatching on the first word of each command line.


CHAPTER 4: MULTITHREADING AND CONCURRENCY CONTROL

4.1 Thread Model

The main thread parses options, starts the components and reads commands in
daemon mode. A single watcher thread blocks on the WatchService. A fixed worker
pool, four threads by default, parses and registers notices. A single audit
writer thread drains log records to disk. A shutdown hook flushes the log and
writes the final board when the user interrupts the program.

4.2 The ExecutorService and the BlockingQueue

The pool is created with Executors.newFixedThreadPool and a thread factory that
names each thread, for example circularsync-worker-1, and installs an
uncaught-exception handler, which makes the audit log readable. Rather than
submitting one task per file, the daemon submits one long-lived consumer loop
per thread, connected to the watcher through a LinkedBlockingQueue bounded at
1,024 paths. Each worker blocks on take until a path is available. The bound
provides back-pressure: if files arrive faster than they can be parsed, the
watcher waits up to five seconds and then logs a saturation event instead of
letting memory grow without limit.

Shutdown uses the poison-pill technique. The daemon closes the WatchService,
then places one sentinel path per worker on the queue. Because the sentinels
sit behind any remaining work, every queued file is still processed before the
workers exit. The sentinel is compared by identity, so a real file of the same
name cannot be mistaken for it.

4.3 Race Conditions and Their Prevention

Duplicate events are the first race. Most operating systems report a creation
followed by several modifications for one save. A concurrent set of queued
paths ensures that a path is waiting in the queue at most once, and the
recorded fingerprint discards later events for content already handled. In the
live run the daemon observed six events and suppressed two this way.

Concurrent processing of one file is the second. An edit made while a worker
is parsing re-enqueues the path, and a second worker may take it; if both
registered concurrently, the older version could win. A per-path ReentrantLock,
held in a ConcurrentHashMap, makes the second worker wait, after which it sees
the newer fingerprint and processes the new content.

Partially written files are the third. A creation event can arrive before a
copy finishes, so the worker polls size and modification time every 120
milliseconds until they are stable.

4.4 Thread-Safe Collections in the Registry

The primary store is a ConcurrentHashMap from identifier to notice, giving
lock-free lookups. A second ConcurrentHashMap maps source file names to
identifiers, enabling replacement on edit and withdrawal on deletion. Category
and keyword indexes are ConcurrentHashMaps whose values are concurrent sets
from ConcurrentHashMap.newKeySet.

The ranked board is a TreeSet. Because TreeSet is not thread-safe and each
registration must update five structures atomically, every mutation holds the
write lock of a ReentrantReadWriteLock and every ranked view holds the read
lock, so many readers proceed in parallel while writers have exclusive access.
Searches and point lookups read only the concurrent maps and need no lock.

Deadline queries use a PriorityQueue as a min-heap ordered by deadline and then
score, so the soonest deadline is listed first regardless of priority. This
complements the TreeSet, which orders by priority.

4.5 Visibility and Draining

Every field of a notice is written by one worker, and the final write sets a
volatile processed flag. The Java Memory Model makes all earlier writes visible
to any thread that reads the flag, and publication through the registry's lock
and concurrent maps also establishes happens-before ordering. Published notices
are never modified. Statistics use AtomicLong counters.

Scan mode and the tests must know when all work has finished. The daemon keeps
an in-flight counter guarded by a monitor, incremented on enqueue and
decremented in a finally block when a worker finishes. The method awaitIdle
waits on the monitor until the count reaches zero. The finally block ensures a
failure in one file can never leave the counter raised.


CHAPTER 5: JAVA NIO AND FILE MANAGEMENT ENGINE

5.1 The WatchService Event Loop

The daemon registers the incoming directory with a WatchService for creation,
modification and deletion events. The watcher calls take, which blocks without
consuming processor time, then drains events with pollEvents. An overflow event,
meaning the operating system discarded events, triggers a warning and a full
rescan so no file is permanently missed. Deletions withdraw notices, and
creations or modifications of supported files enqueue the path. The key is then
reset; if it is no longer valid, the daemon logs an error and the loop ends.
Closing the WatchService makes a blocked take throw
ClosedWatchServiceException, which the loop catches to exit cleanly without
polling.

5.2 Path and Files API Usage

Paths are normalised to absolute form before use as map keys. The initial scan
uses Files.newDirectoryStream in try-with-resources. Files.readAttributes with
BasicFileAttributes returns size and modification time in one call. Files.size
rejects oversized files before they are loaded. Content is read with
Files.newBufferedReader and an explicit UTF-8 charset, and a leading byte-order
mark written by some Windows editors is removed. Log directories are created
with Files.createDirectories.

5.3 Asynchronous Audit Logging

If workers wrote directly to disk, a slow disk would slow parsing. The
AuditLogger separates producing a record from writing it. A call to log formats
a line with timestamp, severity, thread name, event code and detail, offers it
to a bounded LinkedBlockingQueue, and returns at once; if the queue stays full
for fifty milliseconds the record is counted as dropped rather than stalling
the caller. A dedicated writer thread opens the file once with
Files.newBufferedWriter using CREATE, APPEND and WRITE, inside a
try-with-resources block spanning the logger's life. It takes a record, drains
any others waiting, writes them as a batch and flushes once. Because only one
thread writes, lines never interleave. Closing the logger enqueues a sentinel
and waits for the writer, guaranteeing every accepted record reaches disk.

5.4 Atomic Snapshots and Format Flexibility

The ranked board is written to processed_notices.txt after each scan and when
the daemon stops. It is first written to a temporary file and then moved over
the target with Files.move using ATOMIC_MOVE and REPLACE_EXISTING, so readers
never see a half-written board. If atomic moves are unsupported, an ordinary
replacing move is used.

The parser accepts plain text and Markdown. Markdown headers may be written as
list items with bold keys; the normaliser strips these markers before matching.
Lines beginning with a hash, comments in plain text and headings in Markdown,
are ignored in the header block, so one file reads well in a Markdown viewer and
still parses correctly.


CHAPTER 6: EXCEPTION HANDLING AND SYSTEM RESILIENCE

6.1 Custom Exception Hierarchy

The root exception, CircularSyncException, extends Exception and carries the
source file name. InvalidNoticeFormatException is thrown when a file cannot be
interpreted. It records an optional line number and builds a consistent message
naming the file, the line and the problem, such as a missing or duplicate
header, an empty value, an unparseable date or an unknown type. In the live
run, a deliberately broken file was rejected with a message listing its six
missing headers, telling the issuing office exactly what to correct.
ExpiredDeadlineException is thrown when a valid notice's deadline precedes the
processing date, and carries both dates. Expired notices are logged rather than
displayed, since an action that can no longer be taken only adds noise.

These exceptions are checked so that the compiler forces callers to handle
parsing failures. Programming errors, such as calling parseMetadata before
validateFormat, raise unchecked IllegalStateException instead, because they
indicate a defect in code rather than in input.

6.2 Input Validation Pipeline

Validation proceeds in layers of increasing cost. The parser checks the
extension and ignores hidden and swap files; rejects empty files and files over
256 kilobytes; reads UTF-8 and converts malformed encoding into a format
exception; and detects the type before constructing any object. The notice then
checks for a terminator line, the KEY colon value shape, duplicate keys, empty
values, all required headers, agreement between declared type and subclass,
and a non-empty body. Parsing rejects a deadline or examination date before the
issue date, a grade point requirement above ten, a negative seat count and an
empty keyword list. Only then does the deadline check run.

6.3 Resource Safety and Recovery

Every stream, reader, writer and directory handle is opened in a
try-with-resources statement, as are the audit logger and daemon in scan mode,
both of which implement AutoCloseable. This matters particularly on Windows,
where an open handle prevents a file from being replaced or deleted.

The worker loop handles each failure separately. A format or expiry rejection
is counted, logged and causes any earlier version of the file to be withdrawn.
A NoSuchFileException, caused by deletion between event and read, is treated
as normal. Any other IOException, such as a sharing violation, is logged and
the fingerprint cleared so the next event retries the file. A RuntimeException
from an unexpected defect is caught and logged at loop level, so one bad file
can never kill a worker and silently shrink the pool. InterruptedException is
never swallowed; the interrupt status is restored. The Main class maps failures
to exit codes: two for incorrect usage, one for input and output failure, and
130 for interruption.


CHAPTER 7: MODULE DESCRIPTION AND CODE ANATOMY

7.1 Package Structure

The source tree under src/com/circularsync contains six packages: model for
the notice hierarchy and category enumeration, interfaces for Processable,
exceptions for the three exception classes, service for the parser, registry
and audit logger, daemon for the directory watcher, and main for the entry
point and query console. Tests live in a separate test tree.

7.2 The model Package

NoticeCategory defines EXAM, PLACEMENT and CLUB, each with an identifier prefix,
a display name and a case-insensitive lookup. The validateFormat method of
Notice normalises line endings, walks the lines until the terminator, matches
each against a regular expression requiring an upper-case key, a colon and a
value, and collects headers into an insertion-ordered map. Each subclass
declares immutable sets of required headers, immutable keyword-weight maps and
a category base score.

7.3 The service Package

NoticeParserService holds only a supplier of the reference date, injected
through its constructor. Production code supplies the system date, while tests
and the today option supply a fixed date, making every score in this report
reproducible. With no mutable state, one instance is shared by all workers.

NoticeRegistry provides register, removeBySource, find, ranked, top,
byCategory, search, dueWithin, countsByCategory and size. Search tokenises the
query by lower-casing it and splitting on characters other than letters,
digits and hyphens, discards stop words and very short tokens, then intersects
the identifier sets of each term, giving AND semantics. The index covers the
title, keywords, body and every non-date header value. The find operation
accepts a full identifier or a unique prefix, so typing EXM suffices when only
one examination notice is active.

7.4 The daemon and main Packages

DirectoryWatcherDaemon owns the queue, the queued-path set, per-path locks,
fingerprints, listeners and statistics. Its public methods start, startWorkers,
startWatching, enqueueExistingFiles, awaitIdle and close define the lifecycle.
Nested classes hold the atomic statistics, the file fingerprint and the named
thread factory.

Main parses options with a small parser that validates numeric ranges and
dates, wires the components for each mode, registers the shutdown hook and
writes the board snapshot. QueryConsole interprets list, top, category, search,
due, show, stats, help and quit. Its renderBoard method is shared with the
snapshot writer, so the file on disk always matches the console.

7.5 Build Scripts

The scripts build.sh and build.bat compile all sources with release 17, all
lint warnings and UTF-8 encoding into the out directory, then run the test
suite. They honour JAVA_HOME, which allowed the project to be built with the
JDK bundled with Android Studio on a machine with no JDK on the system path.


CHAPTER 8: VERIFICATION, TESTING AND GIT MANAGEMENT

8.1 Test Methodology

The automated suite, CircularSyncTestSuite, uses no external framework. A small
harness records each test's outcome and the exit code equals the number of
failures, so the suite can gate a build. Every test fixes the reference date at
4 November 2026, so expected scores are exact.

The eighteen tests fall into four groups. Parsing tests confirm that a valid
notice of each category yields the right subclass, fields and exact score, and
that decorated Markdown parses. Rejection tests confirm that a missing header,
bad date, unterminated header, unknown type, empty body and deadline before
issue date each raise InvalidNoticeFormatException with an informative message,
and that a past deadline raises ExpiredDeadlineException. Registry tests cover
ranking, duplicate detection, replacement of an edited file with removal of its
old index terms, AND-semantics search and deadline ordering.

The concurrency test releases eight threads simultaneously through a countdown
latch; each registers fifty notices while repeatedly reading the board and
searching. It confirms that all 400 registrations succeed, the board holds
exactly 400 strictly ordered notices, and the index returns all 400 for a
common term. Two daemon tests use real temporary directories and the real
WatchService. The first runs a mix of valid, malformed, expired and unsupported
files through three workers and checks every count and every audit outcome.
The second writes files into a running daemon, deletes one and rewrites
another, waiting each time for the registry to reflect the change.

8.2 Results

The project compiled sixteen source files with no errors or lint warnings, and
all eighteen tests passed.

Three sample circulars were placed in incoming_notices: an end-semester
examination for CS301 Operating Systems with a hall-ticket deadline of 10
November 2026, a recruitment drive with registration closing on 8 November and
a package of 18.5 lakhs per annum, and a robotics workshop with forty seats
closing on 25 November. Scan mode indexed all three with no rejections or
input and output errors and exited with code zero, ranking the examination
first at 86, the placement second at 77 and the club third at 29. The due
query for seven days listed the placement before the examination because its
deadline is earlier, confirming that the deadline heap orders independently of
score. The show query printed the full examination notice given only the
prefix EXM.

The daemon was then run unattended for seven seconds with three workers. Two
seconds in, a Markdown hackathon circular and a broken examination circular
were dropped into the directory, and both were deleted two seconds later. The
audit log shows the three samples indexed concurrently by three worker threads
within a quarter second, the hackathon indexed with a score of 48 reflecting
its two-day deadline, the broken file rejected with its six missing headers
listed, and the hackathon withdrawn by the watcher when deleted. The final
statistics were seven files queued, four indexed, one rejected for format, one
removed, six events observed, two duplicate events suppressed and zero input
or output errors. The interactive shell, driven with top, search, category, an
unknown command and quit, produced the expected output for each and exited
with code zero.

8.3 Git Management

The workspace was initialised as a Git repository on the branch main. A
gitignore file excludes class files, the out directory, jar and temporary
files, editor configuration and generated audit logs, while a placeholder keeps
the audit_logs directory in the repository. All source, tests, sample notices,
build scripts and the readme were committed with the message "feat: initial
implementation of CircularSync notice daemon, thread pool parser, and NIO watch
service", after which git status reported a clean working tree. This report was
added in a separate documentation commit, keeping implementation and
documentation distinct in the history.


CHAPTER 9: CONCLUSION AND FUTURE SCOPE

9.1 Conclusion

CircularSync shows that the disorder of campus communication can be reduced
substantially with a modest, well-structured program. A light header block
turns announcements into data that can be validated, ranked and queried. The
WatchService makes ingestion automatic; an ExecutorService fed by a bounded
BlockingQueue processes many circulars at once without blocking the watcher;
concurrent collections and a read-write lock keep the registry consistent; and
a TreeSet and a PriorityQueue order notices by priority and by deadline. The
abstract Notice class, its subclasses and the Processable interface keep shared
logic in one place while letting each category define its own ranking and
presentation. Checked exceptions and try-with-resources make every failure
visible and every resource safe. The tests and live runs confirm correct
behaviour under normal operation, concurrent load and malformed, expired,
edited and deleted input.

9.2 Campus Integration

Because the directory is the integration point, adapters can be added
independently: one reading a dedicated email inbox and saving attachments, one
publishing the board as a web page or JSON feed for the college portal. A
preprocessing stage applying optical character recognition to scanned PDFs and
proposing a header block for confirmation would bring legacy circulars into the
system, and a lightweight classifier could suggest TYPE and PRIORITY_KEYS
values.

9.3 Mobile Notification Hooks

The daemon's index listeners currently print to the console, but the same hook
can call a push-notification service, a messaging group or a campus app.
Combined with student profiles recording branch, year and club memberships,
notifications could be targeted, and reminders could be sent automatically
when a deadline enters a configured window.

9.4 Scalability

For one college the in-memory registry is ample. For a university with many
affiliated colleges, a database could back the registry with the in-memory
structures as a cache. Because workers share only the queue and the registry,
the local queue could be replaced by a message broker to distribute processing
across machines, and the watcher could monitor one directory per issuing office
to attribute circulars to their source.

9.5 Closing Remarks

The project met its objectives using only standard Java. It is small enough to
understand completely and complete enough to use, and it changes the question a
student must answer from where the information is to what needs to be done
next.

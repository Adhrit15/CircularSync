CIRCULARSYNC: AN AUTOMATED CAMPUS CIRCULAR PARSING DAEMON AND QUERY SYSTEM

A Project Report on the Design and Implementation of a Concurrent,
File-System-Driven Notice Management Engine and Web Portal in Java

November 2026


ABSTRACT

Colleges issue a large volume of circulars every semester, mostly as PDF and
Word letters spread across unstructured channels, and these circulars are
rarely ranked by urgency, so students routinely miss deadlines with academic or
career consequences. This report presents CircularSync, a Java application that
treats every circular as a document dropped into a monitored directory. A
daemon built on the Java NIO WatchService detects new files in real time, a
fixed-size thread pool fed by a blocking queue extracts, validates and indexes
them concurrently, and a thread-safe in-memory registry keeps every active
notice sorted by priority and deadline. Text is extracted from PDF and Word
documents, and a heuristic structuring stage infers the category, title, dates,
deadline and type-specific details of free-form letters. Notices are modelled
through an abstract base class with four subclasses, an interface defining the
processing contract, and custom checked exceptions. A web portal built on the
JDK's HTTP server shows uploads and the ranked board live, and can be published
on the internet with password-protected administration. The system was verified
with a twenty-six-case automated test suite, browser testing and a live public
deployment, and is maintained under Git version control.


CHAPTER 1: INTRODUCTION AND PROBLEM STATEMENT

1.1 Background

An engineering college of moderate size issues several hundred circulars in an
academic year. The Controller of Examinations publishes schedules and
hall-ticket instructions, the Training and Placement Cell announces recruitment
drives with tight registration windows, student clubs advertise workshops and
competitions, and administrative offices announce fees, scholarships and
holidays. Most of these circulars are written as formal letters and distributed
as PDF or Word files through notice boards, email, class messaging groups and
the college portal. Information that is individually well written becomes
collectively chaotic: students miss hall-ticket windows, register late for
placement drives and learn about workshops after the seats are full.

1.2 Bottlenecks in the Existing Process

Three weaknesses explain the failure. First, circulars have no common
structure: the deadline, the issuer and the expected action are buried in
prose and cannot be extracted mechanically. Second, there is no
prioritisation: an optional quiz and a mandatory end-semester examination
arrive with the same visual weight. Third, there is no single queryable store,
so a student cannot simply ask which deadlines fall within the next week. A
quieter weakness is the lack of accountability: when a circular is corrected or
withdrawn, there is no record of when the change happened.

1.3 Objectives

CircularSync was designed to accept circulars in the formats in which they are
actually published, PDF and Word, as well as a simple structured text format;
to read free-form letters without requiring issuing offices to change how they
write; to detect new or edited circulars automatically within seconds; to
process many circulars concurrently; to reject unusable and expired circulars
with a clear explanation; to rank active circulars by a transparent priority
score; to present the results in a clear web interface that can be opened from
any device; to restrict changes to an administrator when the portal is public;
and to record every event in a durable audit trail.

1.4 Scope

The project delivers a Java application whose only third-party dependency is
Apache PDFBox for PDF text extraction. It covers four categories: examination,
placement, club and general administrative notices. Optical character
recognition for scanned PDFs, persistent database storage and per-student user
accounts are left as future work.


CHAPTER 2: ARCHITECTURAL DESIGN AND SYSTEM FLOW

2.1 Architectural Overview

CircularSync follows a producer and consumer architecture. A watcher observes
the incoming directory and produces work items; a bounded work queue buffers
them; a worker pool converts each file into a notice object; and a registry
stores, indexes and queries notices. Inside each worker, a three-stage
ingestion pipeline acquires text from the file, structures it if it is
free-form, and validates it into a typed notice. Around this core sit an audit
logger that records events without blocking the threads producing them, a
command console for terminal queries, and a web portal that accepts uploads
and serves the live board to browsers.

The components are deliberately decoupled. The watcher knows nothing about
parsing, the workers know nothing about the portal, and the registry knows
nothing about files. The portal never writes to the registry directly:
uploaded files are delivered into the watched directory and travel through
exactly the same WatchService, queue and worker pool as a file copied in by
hand. This single path keeps behaviour identical however a circular arrives.

2.2 Life Cycle of a Notice

An administrator uploads a file such as a placement circular in Word format, or
an office copies it into the incoming directory. The portal writes uploads to a
hidden temporary file and renames it atomically, so the directory only ever
contains complete files. The operating system reports a creation event, the
watcher thread resolves the file name, checks the extension, offers the path to
the work queue and returns to waiting.

A worker thread takes the path and waits until the file has stopped changing,
reading its size and modification time until two consecutive readings agree.
If this fingerprint equals the one recorded for the previous processing of the
same path, the event is a duplicate and is discarded. Otherwise the parser
service acquires the text: plain-text files are read directly, while PDF and
Word files are passed to the document extractor. If the text is not already in
the structured header format, the circular structurer infers the headers from
the prose. The parser then constructs the matching subclass and runs
validation, metadata parsing and the deadline check. The registry reports
whether the notice was added, replaced an earlier version of the same file, or
duplicated existing content. The worker writes an audit record and publishes a
processing event, which the portal's file tracker uses to update the status of
that file in the browser.

A deleted file causes its notice to be withdrawn, an edited file replaces its
old version atomically, and a file that fails validation is audited with the
reason while any earlier valid version of it is withdrawn.

2.3 Operating Modes

Scan mode processes every existing file once, prints the ranked board and
exits. Query mode does the same but runs a single query, which suits scripts.
Daemon mode keeps the watcher running with an interactive terminal prompt. Web
mode adds the portal, either for the local computer only or, with the public
option, for access from the internet. All modes share one pipeline, so
behaviour verified in one holds in the others.

2.4 Design Decisions

The registry is kept in memory because active circulars number in the
hundreds; the source files remain the authoritative record, so the registry can
always be rebuilt by rescanning. The file system is the integration point
because every office can drop a file into a shared folder. The priority score
is computed once at parse time and cached, because recomputing it during
comparisons could leave the sorted collection inconsistent as the date
changes. Finally, free-form circulars are converted into the same structured
header format that hand-written notices use, so the strict validator remains
the single gatekeeper for every notice.


CHAPTER 3: OBJECT-ORIENTED DESIGN PATTERNS

3.1 The Processable Interface

The interface Processable declares validateFormat, which checks structural
shape; parseMetadata, which converts header values into typed fields; and
isProcessed, which reports completion. Both of the first two declare the
checked InvalidNoticeFormatException, forcing every implementation to report
problems uniformly. Separating validation from parsing lets cheap structural
checks reject bad input before any conversion, and lets error messages
distinguish a wrongly shaped file from one with wrong values.

3.2 The Abstract Base Class Notice

The abstract class Notice implements Processable and Comparable. It holds the
state shared by every circular: source file name, raw content, reference date,
headers, body, identifier, title, issuer, issue date, deadline, priority
keywords and cached score. It provides final implementations of validateFormat
and parseMetadata, so subclasses cannot weaken the common checks, and applies
the Template Method pattern: common logic runs first, then calls the protected
hooks getTypeSpecificRequiredHeaders and parseTypeSpecificMetadata. Two public
abstract methods, calculatePriorityScore and formatSummary, express behaviour
that differs between categories, and getCategory ties each subclass to a
constant of the NoticeCategory enumeration.

The base class offers two scoring helpers. The method urgencyPoints implements
a stepped curve awarding forty points when the deadline is at most one day
away, thirty-two within three days, twenty-four within a week, fourteen within
two weeks, six within a month and two otherwise. The method keywordPoints sums
the weights of the notice's keywords from a table supplied by the subclass.
Stepped values were chosen because they are easy to explain to students.

3.3 Inheritance and Method Overriding

ExamNotice adds a course code, examination date, venue and examination type.
Its score combines a base of thirty, the urgency of the action deadline, a
proximity bonus for the examination date, and weights for keywords such as
mandatory and hall-ticket; the sample end-semester notice scored eighty-six.
PlacementNotice adds company, role, eligibility, package, minimum grade point
average and drive date, with a base of twenty-five and a compensation band
bonus; the sample drive scored seventy-seven. ClubNotice adds club name, event
date, venue and seat limit, with a base of only ten and three quarters of the
urgency points, so optional activities never bury mandatory ones; the sample
workshop scored twenty-nine. GeneralNotice, added for fee, scholarship, hostel
and holiday circulars, requires no extra headers and scores a base of fifteen
plus urgency and keywords such as fee and scholarship.

Each subclass overrides formatSummary to present its own fields. The console,
the board snapshot and the portal call these methods through a reference of
the base type, and dynamic dispatch selects the right version at run time.
Adding the fourth category required a new subclass, an enumeration constant
and one line in the factory, and no change to the pipeline, registry or
ranking code, which demonstrates the value of the hierarchy.

3.4 Natural Ordering and Identity

The natural order places the highest score first, then the earliest deadline,
then title, then identifier, making the order total as a TreeSet requires. The
identifier combines a category prefix with the first ten hexadecimal characters
of a SHA-256 digest of the content, so identical files share an identifier and
duplicates are detected cheaply.

3.5 Supporting Patterns

The parser's createNotice method is a Factory Method mapping a category to its
subclass. The daemon publishes processing events to registered listeners, an
application of the Observer pattern that lets the console and the web portal
react to the same pipeline without the daemon knowing either exists. The
document extractor and circular structurer act as a Pipeline of stateless
stages in front of the validator, and the console applies a simple Command
pattern.


CHAPTER 4: MULTITHREADING AND CONCURRENCY CONTROL

4.1 Thread Model

The main thread starts the components and reads terminal commands. A single
watcher thread blocks on the WatchService. A fixed worker pool, four threads by
default, extracts, parses and registers notices. A single audit writer thread
drains log records to disk. The web portal runs its own fixed pool of eight
request threads. A shutdown hook flushes the log and writes the final board
when the program is interrupted or the hosting platform stops it.

4.2 The ExecutorService and the BlockingQueue

The worker pool is created with Executors.newFixedThreadPool and a thread
factory that names each thread, which makes the audit log readable. The daemon
submits one long-lived consumer loop per thread, connected to the watcher
through a LinkedBlockingQueue bounded at 1,024 paths. The bound provides
back-pressure: if files arrive faster than they can be processed, the watcher
waits and then logs a saturation event rather than letting memory grow without
limit. This matters more now that PDF extraction can take tens of milliseconds
per file. Shutdown uses the poison-pill technique: one sentinel path per worker
is queued behind any remaining work, so every queued file is still processed
before the workers exit.

4.3 Race Conditions and Their Prevention

Duplicate events are the first race: most operating systems report a creation
followed by several modifications for one save. A concurrent set ensures a path
waits in the queue at most once, and the recorded fingerprint discards later
events for content already handled. Concurrent processing of one file is the
second: an edit made while a worker is parsing re-enqueues the path, so a
per-path ReentrantLock makes a second worker wait and then process the newer
content. Partially written files are the third: the worker polls size and
modification time until they are stable, and portal uploads avoid the problem
entirely through atomic renames.

A fourth race appeared in the web portal. A browser poll that started just
before an administrator signed in could return after the sign-in and briefly
reset the page to the viewer state. The page now records which credential each
poll used and discards responses issued under a different one.

4.4 Thread-Safe Collections in the Registry

The primary store is a ConcurrentHashMap from identifier to notice, giving
lock-free lookups. A second ConcurrentHashMap maps source file names to
identifiers, enabling replacement on edit and withdrawal on deletion. Category
and keyword indexes are ConcurrentHashMaps whose values are concurrent sets.
The ranked board is a TreeSet; because each registration must update five
structures atomically, every mutation holds the write lock of a
ReentrantReadWriteLock and every ranked view holds the read lock, so many
portal requests can read in parallel. Deadline queries use a PriorityQueue as a
min-heap ordered by deadline. The portal's file tracker and the rate limiter
also hold shared state; the tracker synchronises its small collections, and
the limiter keeps per-client counters in a ConcurrentHashMap.

4.5 Visibility and Draining

Every field of a notice is written by one worker, and the final write sets a
volatile processed flag, so the Java Memory Model makes all earlier writes
visible to any thread that reads it; published notices are never modified.
Statistics use AtomicLong counters. An in-flight counter guarded by a monitor,
decremented in a finally block, lets scan mode and the tests wait until all
work has finished.


CHAPTER 5: JAVA NIO, FILE MANAGEMENT AND DOCUMENT EXTRACTION

5.1 The WatchService Event Loop

The daemon registers the incoming directory for creation, modification and
deletion events. The watcher calls take, which blocks without consuming
processor time, then drains events with pollEvents. An overflow event triggers
a full rescan so no file is missed; deletions withdraw notices; creations and
modifications of supported files enqueue the path. Closing the WatchService
makes a blocked take throw ClosedWatchServiceException, which ends the loop
cleanly without polling.

5.2 Path and Files API Usage

Paths are normalised to absolute form before use as map keys. Directory scans
use Files.newDirectoryStream in try-with-resources, attributes are read with
Files.readAttributes, and oversized files are rejected with Files.size before
they are loaded. Plain text is read with Files.newBufferedReader and an
explicit UTF-8 charset. Portal uploads are written with Files.createTempFile
and Files.write and then moved into place with Files.move using ATOMIC_MOVE and
REPLACE_EXISTING.

5.3 Document Text Extraction

PDF text is extracted with Apache PDFBox 3.0.3, reading at most forty pages and
sorting text by position so letterheads read in order. A PDF with no
selectable text, which is usually a scanned image, is rejected with that
explanation, and a password-protected PDF is reported as such. Word documents
are handled with the JDK alone: the .docx file is opened as a ZIP archive, the
part word/document.xml is read, and its XML is streamed through StAX, emitting
paragraph, line and tab breaks. Because uploads may come from the internet,
DTD processing and external entities are disabled to prevent XML external
entity attacks, and the decompressed XML is capped at twenty megabytes to
defeat ZIP bombs. Extracted text is capped at 200,000 characters.

The PDFBox jars are not stored in the repository. A small build tool downloads
them from Maven Central and verifies each against a pinned SHA-256 checksum, so
a tampered or corrupted dependency fails the build.

5.4 Inferring Structure from Free-Form Circulars

Real circulars are letters, not forms. The CircularStructurer reads them with
transparent heuristics. The category is chosen from weighted vocabulary: terms
such as examination, hall ticket and revaluation suggest an examination notice;
recruitment, campus drive and LPA a placement notice; club, workshop and
hackathon a club notice; and anything below a confidence threshold becomes a
general notice. The title is taken from a "Subject:" line, otherwise the first
substantive line that is not a letterhead or reference. Dates are recognised in
ISO form, day-first numeric form such as 15/11/2026 or 15.11.26, and written
form such as 15th November 2026. The issue date comes from a "Date:" line, and
the deadline from the date nearest a cue such as "last date", "on or before",
"register by" or "closes on". The issuer is taken from the signature block.
Type-specific fields such as course codes, venues, company names, packages,
eligibility, club names and seat limits come from labelled lines and common
patterns, with safe defaults when absent.

The structurer writes its findings as an ordinary header block and records two
extra headers: the original format, and the list of fields it had to infer. The
original text becomes the notice body unchanged. A file that begins like a
structured notice is never inferred; it is validated strictly, so a mistake in
a hand-written notice is reported rather than silently guessed.

5.5 Asynchronous Audit Logging

The AuditLogger separates producing a record from writing it. A call to log
formats a line and offers it to a bounded queue, returning at once. A dedicated
writer thread holds the file open with Files.newBufferedWriter in
try-with-resources, writes queued records in batches and flushes once per
batch, so lines never interleave. The ranked board is written to a snapshot
file through a temporary file and an atomic move, so readers never see a
half-written board.


CHAPTER 6: EXCEPTION HANDLING, RESILIENCE AND SECURITY

6.1 Custom Exception Hierarchy

The root exception, CircularSyncException, carries the source file name.
InvalidNoticeFormatException is thrown when a file cannot be interpreted and
builds a consistent message naming the file, the line where relevant and the
problem. The same exception now covers extraction failures, such as a scanned
PDF, a password-protected PDF or a damaged Word document. ExpiredDeadlineException
is thrown when a valid notice's deadline precedes the processing date and
carries both dates. Both are checked, so the compiler forces callers to handle
them, while programming errors raise unchecked IllegalStateException.

6.2 Input Validation Pipeline

Validation proceeds in layers of increasing cost: extension and hidden-file
checks; size limits of 256 kilobytes for text and fifteen megabytes for PDF and
Word files; text extraction with its own limits; structuring; and finally the
strict header validation and metadata parsing, which reject impossible dates,
deadlines before the issue date, out-of-range values and empty keyword lists.
The portal adds a further check before a file reaches the folder: the first
bytes must match the claimed type, so a renamed executable is refused as not a
real PDF.

6.3 Resource Safety and Recovery

Every stream, reader, writer, ZIP file, PDF document and directory handle is
opened in a try-with-resources statement. The worker loop handles each failure
separately: rejections are counted, logged and shown in the portal with their
reason; a file deleted before it could be read is treated as normal; other
input and output errors are logged and retried on the next event; and an
unexpected runtime exception is caught at loop level so one bad file can never
shrink the worker pool.

6.4 Security for Public Deployment

Publishing the portal on the internet required protecting it. Anyone may view
the board, but uploads, deletions and demo drops require an administrator
password. The password is chosen by the administrator, either as an environment
variable or a command-line option; if the portal is made public without one, a
random password is generated and printed so the portal is never left open. The
browser sends the password in a request header, percent-encoded so that
spaces, symbols and non-English letters survive, and the server compares it in
constant time. A client that sends ten wrong passwords within ten minutes is
locked out, and writes are limited to sixty per client per ten minutes. Behind
a proxy or tunnel the real client address is read from forwarding headers.
File names are whitelisted against path traversal, and every response carries
defensive headers, including a content security policy, a frame denial and a
no-sniff directive; original documents are served under a sandbox policy.


CHAPTER 7: MODULE DESCRIPTION AND CODE ANATOMY

7.1 Package Structure

The source tree under src/com/circularsync contains twenty-five classes in
seven packages. The model package holds the notice hierarchy and category
enumeration; interfaces holds Processable; exceptions holds the three
exception classes; service holds the parser, document extractor, circular
structurer, registry and audit logger; daemon holds the directory watcher and
its processing event and listener types; web holds the portal server, its
settings, the file activity tracker, the rate limiter and a small JSON writer;
and main holds the entry point and query console. The test suite lives in a
separate tree, build tools in tools, and the portal page in web/index.html.

7.2 The service Package

NoticeParserService holds only a supplier of the reference date, injected so
that tests can fix the date. It chooses the size limit by type, acquires text
through the extractor for PDF and Word files, sends free-form text through the
structurer, and then performs the factory and validation steps.
DocumentTextExtractor and CircularStructurer are stateless and shared by all
workers. NoticeRegistry provides registration, removal, lookup by identifier or
prefix, ranked and top views, category and keyword search with AND semantics,
deadline queries and statistics.

7.3 The daemon Package

DirectoryWatcherDaemon owns the queue, the queued-path set, per-path locks,
fingerprints, statistics and listeners. Its public methods start, startWorkers,
startWatching, enqueueExistingFiles, awaitIdle and close define the lifecycle.
ProcessingEvent is an immutable record of one outcome, such as indexed,
rejected for format, rejected as expired or removed, and ProcessingListener is
the callback interface through which the portal observes outcomes.

7.4 The web Package

WebPortalServer is built on com.sun.net.httpserver.HttpServer. It serves the
single-page portal and a JSON interface: a state endpoint returning statistics,
tracked files, the filtered board and recent activity; endpoints for one
notice, the original file, uploads, deletions and demo drops; and a health
endpoint for hosting platforms. FileActivityTracker records every file and its
latest outcome, whether uploaded or copied into the folder, together with an
activity feed. PortalSettings carries the host, port, password and proxy
configuration, and RateLimiter implements fixed-window counters.

The portal page is a single HTML file with no framework. It polls the state
endpoint every 1.2 seconds and re-renders only the sections that changed. The
Uploads tab provides a drag-and-drop area, one-click demo files and a table of
tracked files with live status, results and reasons. The Notice Board tab
shows ranked cards with score rings, category colours, deadline pills, format
chips and auto-detected markers, with search, category and deadline filters, a
detail panel that lists inferred fields and links to the original document, and
a live activity feed. It adapts to light and dark themes and to phone screens.

7.5 The main Package and Deployment Files

Main parses options, wires the components for each mode, resolves the
administrator password and registers the shutdown hook. QueryConsole
interprets terminal queries. A Dockerfile builds the application from source in
a JDK image, verifies the dependencies, and runs it as a non-root user in a JRE
image, honouring the platform's port variable. A Render blueprint describes a
free web service that asks the administrator for the password at creation.


CHAPTER 8: VERIFICATION, TESTING AND GIT MANAGEMENT

8.1 Test Methodology

The automated suite uses no test framework; a small harness records outcomes
and the exit code equals the number of failures. Every test fixes the
reference date at 4 November 2026, so expected scores are exact. The
twenty-six tests fall into six groups. Parsing tests confirm the correct
subclass, fields and score for each structured category and for decorated
Markdown. Rejection tests cover missing headers, bad dates, unterminated
headers, unknown types, empty bodies, inverted dates and expired deadlines.
Registry tests cover ranking, duplicates, replacement of edited files, search
and deadline ordering, and a concurrency test releases eight threads at once to
register four hundred notices while reading the board, then checks that the
board is complete and strictly ordered.

Document tests generate real files during the run: a free-form examination
letter, a Word placement circular built as a genuine .docx archive, and a PDF
club circular produced with PDFBox. Each must be classified correctly with the
right title, deadline, secondary date and type-specific fields. Further tests
confirm the fallback to the general category, the rejection of a PDF without
text and of a corrupt Word file. Daemon tests use real directories and the real
WatchService for creation, modification and deletion. Portal tests run the
HTTP server: uploads, demo drops, filtering, deletion, refusal of path
traversal, unsupported types and fake PDFs, and, with a password containing
spaces, a plus sign and an accented letter, refusal without the password,
acceptance with it, and lockout after repeated wrong attempts.

8.2 Results

Twenty-six source files compiled with no errors or lint warnings, and all
twenty-six tests passed. With the reference date fixed, the structured samples
ranked the examination notice first at 86, the placement drive at 77 and the
club workshop at 29, and an urgent re-examination dropped in during a live run
rose to the top at 100. Two free-form demonstration documents written like real
college letters were processed through the portal: a Word placement circular
was classified as a placement notice with its company, role, package of 12
LPA, deadline of 10 November and drive date of 17 November all detected,
scoring 85; a PDF scholarship circular was classified as a general notice with
its deadline read from "on or before 18th November 2026" and its issuer from
the signature, scoring 55. A malformed notice and an expired notice were
rejected with their reasons shown in the portal.

The portal was tested in a browser for both access levels, for light and dark
themes and at phone width, without console errors. It was then published
through a Cloudflare quick tunnel and opened from its public address, where the
board loaded for an anonymous visitor and an anonymous upload attempt was
refused. Testing the sign-in through the public address exposed two usability
faults: a password copied from the terminal could carry its label or a line
break, and a background poll could briefly undo a fresh sign-in. Both were
corrected and re-verified. Docker was not available on the development
machine, so the container image is built by the hosting platform rather than
locally.

8.3 Git Management

The project is maintained in a Git repository on the main branch and published
on GitHub. A gitignore file excludes compiled classes, the out and lib
directories and generated audit logs. The history records the project's
evolution as separate, descriptive commits: the initial implementation of the
daemon, thread pool parser and NIO watch service; the academic report and its
condensed version; the live demonstration guide; the web portal with live
upload tracking; PDF and Word support with public deployment; the sign-in fix
for pasted passwords; the switch to an administrator-chosen password; and this
updated report. Each commit was pushed after the tests passed.


CHAPTER 9: CONCLUSION AND FUTURE SCOPE

9.1 Conclusion

CircularSync shows that the disorder of campus communication can be reduced
substantially with a well-structured program. It accepts circulars in the PDF
and Word formats in which they are actually published, reads free-form letters
with transparent heuristics, and turns them into data that can be validated,
ranked and queried. The WatchService makes ingestion automatic; an
ExecutorService fed by a bounded BlockingQueue processes many circulars at
once; concurrent collections and a read-write lock keep the registry
consistent; and a TreeSet and a PriorityQueue order notices by priority and by
deadline. The abstract Notice class and its four subclasses show how
inheritance and overriding let a new category be added without touching the
pipeline. Checked exceptions, try-with-resources and layered validation make
every failure visible and every resource safe, and the password-protected web
portal makes the results available to anyone, on any device, while keeping
changes in trusted hands.

9.2 Future Scope

The most valuable extension is optical character recognition, so that scanned
circulars can be read; a preprocessing stage could also let an administrator
confirm inferred fields before publication. The structuring heuristics could
be complemented by a trained classifier, with the current rules kept as an
explainable fallback. An adapter reading a dedicated email inbox would remove
even the upload step.

The daemon's processing events already drive the portal and could equally
call a push-notification service or a messaging group. Combined with student
profiles recording branch, year and club memberships, notifications could be
targeted, and reminders sent automatically when a deadline enters a configured
window. Individual accounts would also allow several administrators with their
own passwords instead of one shared password.

For scalability, uploaded circulars and the registry could be stored in a
database or object store so that they survive redeployment on free hosting
tiers, with the in-memory structures acting as a cache. Because workers share
only the queue and the registry, the local queue could be replaced by a message
broker to spread processing across machines.

9.3 Closing Remarks

The project met its objectives with standard Java and a single, verified
dependency. It is small enough to understand completely and complete enough to
use, and it changes the question a student must answer from where the
information is to what needs to be done next.
